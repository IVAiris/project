# План реализации MVP за 24 часа

Ниже — рабочий план на **24 часа** для проекта.
Его смысл: сначала перенести проверенный паттерн из терминального урока — `ai_client.py`, `agent_runtime.py`, tools, `soul.md`, `.env`, ограничения и логи — а затем добавить только обязательную веб-обвязку проекта.
Терминальный урок уже даёт корректную основу: модель выбирает tool, Python валидирует вызов, выполняет разрешённую функцию и возвращает результат модели; система не должна доверять prompt как механизму безопасности.

## Реалистичный объём

MVP:

> **ЮрСправочник — веб-чат с ИИ-консультантом по внутренней базе знаний юрдепартамента. Пользователь получает консультацию по типовым вопросам и шаблонам, может подготовить черновик по утверждённому шаблону или передать нетиповой вопрос юристу.**

Оставить ровно три услуги:
1. Консультация по типовым вопросам и шаблонам.
2. Подготовка черновика по утверждённому шаблону.
3. Передача вопроса юристу.

Это даёт необходимый каталог из 3–5 услуг, не требует работы с загрузкой файлов или document review и позволяет показать обычную и AI-подготовленную заявки.

## Зафиксированные технические решения

- **Backend:** FastAPI + uvicorn (единый ASGI-процесс — один Python runtime, встроенная pydantic-валидация для HTTP-слоя и для аргументов tools, неблокирующий I/O на время ожидания ответа AI Studio API).
- **FAQ-категория «стоимость»:** для внутренней легенды ЮрСправочника (сервис для сотрудников компании, не внешний платный сервис) категория переосмыслена как **SLA/сроки/приоритет обращения** — сохраняет формальное требование урока о четырёх FAQ-категориях без искусственных внешних цен.

## Минимум content

Не тратить время на большую базу знаний.
Достаточно трёх небольших Markdown-файлов и около 1 500–2 500 слов суммарно:

```text
knowledge/
├── services.md   # 3 услуги, порядок работы, сроки, формат
├── faq.md        # 4 категории FAQ: услуги, SLA/сроки/приоритет, формат работы, правила/контакты
└── rules.md      # границы консультанта, регламент обращения,
                  # описания шаблонов и типовых кейсов
```

Для демонстрации подготовить 6–8 точных вопросов, на которые в этих файлах есть очевидные ответы: “где найти шаблон”, “какие данные нужны для черновика”, “когда направлять вопрос юристу”, “какой срок первичного ответа”. ИИ должен сначала обращаться к базе, а не отвечать общими знаниями.

## Самые опасные точки

Не начинать эти задачи до прохождения базовых сценариев:

- Загрузка и анализ пользовательского файла.
- Автоматическая проверка договора по чек-листу.
- Генерация полного юридического документа.
- Векторная БД, embeddings и внешний RAG-сервис.
- Авторизация, роли, личный кабинет.
- Интеграции с СЭД, 1С, e-mail, Telegram.
- Реальная отправка обращения в корпоративную систему.

Они не нужны для заданного agent pattern или основного проекта и критически увеличивают риск не успеть сделать обязательные сценарии, README, VPS и доказательства.

## Точка роста (архитектурный резерв, не MVP)

Подключение RAG и локальной LLM в текущий 24-часовой MVP не входит, но архитектура должна допускать это без переделки UI и `bot_flow.py`:

- `ai_client.py` — единая точка подключения источника модели, чтобы позже заменить AI Studio на локальную LLM без изменения `agent_runtime.py`.
- `search_knowledge` — отдельная функция/модуль, чтобы позже заменить файловый поиск на RAG.
- `knowledge/` — короткие структурированные Markdown-файлы, чтобы упростить будущий chunking и индексацию.
- `agent_runtime.py` — tool-логика не смешивается с HTTP/UI-слоем, чтобы retrieval-бэкенд можно было сменить отдельно.

В MVP реализуются только: AI Studio API как единственный источник ответов, `knowledge/` как локальная файловая база, `search_knowledge`/`read_knowledge_file` как файловые tools — без embeddings, vector DB, chunking-пайплайна, ingestion-сервиса и локального inference.

## Стратегия реализации

Самый безопасный порядок:

1. Сначала обычный чат + SQLite без AI.
2. Затем AI Studio + tools в терминале или через простой endpoint.
3. Потом подключить AI к web-интерфейсу.
4. В самом конце сделать deployment и доказательства.

Так останется работающий продукт даже при проблеме с API, а проектное требование базового `bot-flow` без LLM будет закрыто.
