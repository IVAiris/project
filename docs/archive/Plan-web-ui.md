# Plan-web-ui.md — Фаза «Web UI»

## 0. Контекст

Тип проекта: учебный (24-часовой MVP «ЮрСправочник»). Уровень плана: **micro** — покрывает одну фазу из `project_plan_24h.md` («5:30–8:30 Web UI»), не весь проект.

**Предыдущий слой:** `docs/archive/Plan-bot-flow.md` («Обычный бот», закрыт) — `bot_flow.py` готов: каталог услуг, FAQ, полная state-machine заявки и обратной связи, чистые функции без побочных эффектов (кроме вызова `db.insert_lead`/`insert_feedback`). `docs/archive/Plan-sqlite.md` — `db.py` готов.

**Следующий слой:** «Безопасные tools» (8:30–10:00) и «AI-сценарии» (10:00–12:30) — `agent/tools.py`, реальное подключение ИИ-консультанта к `agent_runtime.py`. На этой фазе кнопка «ИИ-консультант» **не подключается по-настоящему** (решено 2026-08-30) — показывает ветку «недоступен» из `docs/bot-ux-flow.md` §6/§10, честно и без новой UX-ветки.

## 1. Статус

Приоритет: высокий — последняя фаза перед тем, как ИИ-консультант и tools станут видны пользователю; фиксирует HTTP/сессионный контракт, которым будут пользоваться все последующие фазы. Текущее состояние: не начато, `app.py`/`static/` в репозитории нет. Секреты не участвуют (эта фаза не трогает `.env`/AI Studio). Источник контекста: `docs/design-decisions.md` (визуальный стиль, все 5 экранов утверждены), `docs/bot-ux-flow.md` (флоу и тексты), `bot_flow.py`/`db.py` (готовая логика), `spec.md` §5 (контракт сессии), `urok.md` (Фаза 2, критерии приёмки).

## 1.1 Целевой сценарий

Конечный пользователь открывает `http://localhost:8000/` в браузере → видит стилизованный по `design-decisions.md` главный экран (хедер с «ЮрСправочник»/«FAQ»/«Обратная связь», приветственное сообщение бота, quick-reply кнопки услуг, кнопка «Перейти к ИИ-консультанту») → кликает «Услуги» или карточку конкретной услуги → видит табы «Регламентный срок»/«Ожидаемый результат»/«Получить услугу» → нажимает «Получить услугу» → проходит пошаговый bot-flow заявки (описание → имя → email → подтверждение) → видит номер заявки → отдельно проверяет «FAQ» (аккордеон) и «Обратная связь» (3 поля) → пробует «ИИ-консультант» и видит честное сообщение о временной недоступности. Всё это работает без `.env`/AI Studio, локально, через один процесс `uvicorn`.

## 2. Требования к результату

**Что должно получиться:** `app.py` (FastAPI, единая точка запуска — по аналогии с `urok.md`, «например, `app.py`»), эндпоинт `POST /api/chat`, раздача статики (`static/index.html`, `static/style.css`, `static/script.js`) с полной стилизацией по `design-decisions.md`, in-memory хранилище сессий, маршрутизация между `bot_flow.py` и веткой «ИИ-консультант недоступен».

**Явные ограничения (что не делаем в этом плане):**
- Не подключаем `agent_runtime.py`/`ai_client.py`/`agent/tools.py` по-настоящему — кнопка «ИИ-консультант» только показывает заглушку недоступности (решено 2026-08-30).
- Не реализуем `cookie`-based persistence, Redis, БД для сессий — только in-memory словарь процесса (`spec.md`, раздел 5, уже зафиксировано).
- Не меняем `bot_flow.py`/`db.py` — эта фаза только вызывает их существующие функции, не переопределяет контракты.
- Не добавляем зависимости сверх `requirements.txt` (`fastapi`, `uvicorn` уже есть).

**Файлы, разрешённые к изменению:** `BOT/project/app.py` (новый), `BOT/project/static/index.html` (новый), `BOT/project/static/style.css` (новый), `BOT/project/static/script.js` (новый), `BOT/project/project_plan_24h.md` (чек-лист по факту), `BOT/project/README.md` (упомянуть `app.py`/`static/` в слоях, если потребуется).

**Снимок API/сессионной модели** (согласовано с пользователем перед черновиком плана):

*Эндпоинт:* `POST /api/chat`
- Запрос: `{"session_id": str | null, "input": str}`.
- Ответ: `{"session_id": str, "reply": str, "buttons": [{"label": str, "value": str}], "is_error": bool}`.
- `is_error` (добавлено 2026-08-30, после обновления `design-decisions.md` до дизайн-системы) — сигнал фронтенду покрасить `reply` в `--jr-danger` (§4.1/§4.2/§7 `design-decisions.md`: ошибка не должна передаваться только цветом, но обязана его использовать). `True`: (а) `bot_flow` вернул тот же `step`, что был до вызова, — признак отклонённого ввода на любом шаге `lead_flow`/`feedback_flow`; (б) неизвестный `service_key` в `service:<key>`/`lead:<key>`; (в) ветка «ИИ-консультант недоступен». Иначе `False`. Определяется в `app.py` сравнением `step` до/после — не требует изменений в уже закрытом `bot_flow.py`.
- `session_id = null` или неизвестный/устаревший — backend создаёт новую сессию молча (`docs/bot-ux-flow.md`, раздел 11 — «истёкшая/ненайденная сессия»), не отдельный экран-предупреждение.
- `session_id` генерируется через `uuid.uuid4().hex` (стандартный выбор, не конфликтует ни с чем зафиксированным).
- **Роут объявляется как обычный `def`, не `async def`.** `db.py`/`bot_flow.py` синхронные, а модель «новое соединение на вызов» в `db.py` спроектирована именно под то, что FastAPI прогонит такие вызовы через свой threadpool (см. `CLAUDE.md`, раздел 4). `async def` с прямым вызовом этих функций без `run_in_threadpool` блокировал бы event loop — избыточно и противоречит уже зафиксированному обоснованию.

*Хранилище сессий* (`SESSIONS: dict[str, dict]`, модуль `app.py`, в памяти процесса — `spec.md` раздел 5):
```
SESSIONS[session_id] = {
    "mode": "main_menu" | "lead_flow" | "feedback_flow",
    "flow_state": dict | None,  # ровно объект flow_state из bot_flow.py, только для lead_flow/feedback_flow
}
```
Поля для истории сообщений в сессии намеренно нет (решено 2026-08-30): при перезагрузке
страницы лента чата стартует заново — так уже предписано `spec.md` раздел 5
(«`localStorage`/persistence не используются для истории сообщений»), восстановление
ленты потребовало бы нового, нигде не предусмотренного механизма. Frontend хранит
отображаемые сообщения только в памяти вкладки браузера (JS-переменная), не персистентно.

**Аварийный выход из середины визарда заявки/feedback — не реализуется** (решено
2026-08-30). `urok.md` не требует возможности прервать сценарий до завершения
(«неизвестный ввод не ломает сценарий» — про невалидный ввод, не про досрочный
выход), а добавление такой кнопки означало бы менять уже закрытую фазу
`bot_flow.py` и усложнять навигацию вопреки принципу минимализма
`project_plan_24h.md`. Пользователь выходит из визарда только через штатный
экран подтверждения (`"back"`), как и было спроектировано в `bot_flow.py`.

*Словарь входных токенов `input` при `mode == "main_menu"`* (обязательная точная схема — источник для фронтенда и бэкенда одновременно):

| `input` | Действие backend |
|---|---|
| `"services"` | `bot_flow.get_services()` → рендер списка карточек-кнопок |
| `"service:<key>"` | `bot_flow.get_service_card(key)` → рендер карточки с 3 табами (данные) |
| `"faq"` | `bot_flow.get_faq()` → рендер аккордеона |
| `"lead"` | `mode="lead_flow"`, `flow_state=bot_flow.start_lead_flow(None)` |
| `"lead:<key>"` (из таба «Получить услугу») | `mode="lead_flow"`, `flow_state=bot_flow.start_lead_flow(key)` |
| `"feedback"` | `mode="feedback_flow"`, `flow_state=bot_flow.start_feedback_flow()` |
| `"ai"` | Ответ веткой недоступности (`docs/bot-ux-flow.md` §6/§10), `mode` не меняется |
| что-либо ещё | `bot_flow.handle_unknown_input()` |

*При `mode == "lead_flow"`:* `input` передаётся как есть в `bot_flow.handle_lead_input(flow_state, session_id, input)`; если новый `state["step"] is None` — `mode` возвращается в `"main_menu"`.

*При `mode == "feedback_flow"`:* аналогично через `handle_feedback_input`; при `step is None` — `mode` → `"main_menu"`.

**Названия услуг — два поля, разные назначения** (решено 2026-08-30, синхронизировано с `docs/bot-ux-flow.md` §3): `SERVICES[i]["name"]` — полное название (используется в тексте карточки/каталога/сводки заявки), `SERVICES[i]["short_name"]` — короткая подпись кнопки, дословно как в макете (`docs/bot-ux-flow.md`, §2/§4: «Согласование договоров», «152-ФЗ (персональные данные)», «Согласование сделок» — короткие названия услуг живут в UX-документе, не в дизайн-системе). Кнопки везде используют `short_name`, текст ответа — `name`.

**Рендеринг данных в текст ответа** (backend формирует `reply`/`buttons` из сырых структур `bot_flow.py` — это тоже часть контракта этой фазы, не решено в предыдущих фазах):
- `get_services()` → `reply` = приветственный текст + список услуг с `description`; `buttons` = по одной на услугу, подпись `short_name` (`value="service:<key>"`) + «Перейти к ИИ-консультанту» (`value="ai"`).
- `get_service_card(key)` → `reply` содержит `name`/`deadline`/`result`; `buttons` = `[{"Получить услугу", "lead:<key>"}, {"Вернуться на предыдущий экран", "services"}]` (табы «Регламентный срок»/«Ожидаемый результат» — переключение на клиенте между уже присланными данными, без повторного запроса).
- `get_faq()` → **точная структура утверждённого макета** (решено 2026-08-30, `docs/bot-ux-flow.md` §4 — структура аккордеона живёт в UX-документе, не в дизайн-системе), не исходные 4 категории `bot_flow.FAQ_CATEGORIES` как таковые: 3 кнопки-аккордеона по услугам (подпись — `short_name`) + отдельная кнопка «Правила и контакты». Разворачивание каждой услуги показывает 4 поля: `name` (полное), `deadline` (уже есть в `SERVICES`), и два новых текстовых поля, авторских (не из `knowledge/`, короткая UI-подсказка):
  - «Как подать заявку» — одинаково для всех 3 услуг: «Через кнопку «Получить услугу» на карточке — описать суть вопроса и оставить контакт».
  - «Что представить» — по услуге: `contracts` → «Проект договора и Лист согласования — через папку «Для юридической службы» на диске P:\, не через бота.»; `pdn` → «Документы не требуются — опишите вопрос или ситуацию в диалоге.»; `deals` → «Пояснительную записку и проект договора — через папку «Для юридической службы» на диске P:\, не через бота.» (согласовано с пользователем — документы не загружаются через бота, `spec.md` раздел 3, «не-цели»).
  «Правила и контакты» — контент как в `bot_flow.FAQ_CATEGORIES["Правила и контакты"]` (уже подходит без изменений, единственная категория из четырёх исходных, которая используется в этой структуре напрямую). Категории «Услуги», «SLA, сроки и приоритет обращения» и «Формат работы» из `FAQ_CATEGORIES` в аккордеоне отдельными кнопками не показываются — их содержание заменено 3 per-service аккордеонами и полями `SERVICES`. `FAQ_CATEGORIES` не удаляется и не редактируется в `bot_flow.py` (правки уже закрытой фазы без необходимости не делаем), три неиспользуемые в этой фазе категории остаются в коде как есть — не техдолг, просто данные, которые эта фаза не читает.

  **Механика раскрытия — сознательное упрощение (2026-08-30).** `design-decisions.md` §6.5 предписывает «оверлей поверх экрана» для развёрнутого текста аккордеона. Ради времени реализовано нативным HTML `<details>`/`<summary>` (инлайн-раскрытие внутри ленты, без модального оверлея) — это по-прежнему настоящий клиентский аккордеон (сворачивается/разворачивается без обращения к серверу), просто другая механика показа контента. API отдаёт структурированные данные (`ChatResponse.faq: [{"title", "body"}]`) отдельно от обычного `reply`, чтобы фронтенд мог отрендерить их именно как `<details>`, а не как плоский текст.
- Шаги `lead_flow`/`feedback_flow` → `reply` = второй элемент кортежа, который уже возвращает `bot_flow.py` (текст готов, рендерить не нужно); `buttons` формируются backend по текущему `step` (например, на `"lead_confirm"` — `submit`/`refine`/`back`).

**Frontend (полная стилизация сразу, решено 2026-08-30):** цвета/шрифты/раскладка — `docs/design-decisions.md`, §4.1 (цвета), §4.3 (типографика), §5.1 (макет/компоновка), §6.4 (карточки-сообщения и кнопки под ними). Отступы и радиус зафиксированы там же (§4.4–4.5) — отдельно запрашивать у пользователя не нужно.

**Новые требования дизайн-системы (обновление `design-decisions.md` 2026-08-30 — документ переструктурирован в чистую дизайн-систему с токенами; старая версия с текстами экранов перенесена в `docs/archive/design-decisions(old).md`, но контент экранов и так брался из `docs/bot-ux-flow.md`, не из неё):**
- Кнопка в состоянии `loading` (ждём ответ `/api/chat`) — недоступна для повторного клика (§6.2).
- `disabled`/`loading` — текст с непрозрачностью ~50%, контраст ≥60%; все остальные состояния — контраст ≥80% (§6.2, §7).
- Ошибка отправки (сетевой сбой `fetch`) не должна терять уже введённый текст — поле ввода не очищается при ошибке (§9). Backend этого не гарантирует (не его слой) — реализуется в `script.js`.
- Сообщения с `is_error=true` (см. «Снимок API» выше) рендерятся текстом `--jr-danger`, не заливкой всей карточки (§5.2).

другими (карточка услуги) — 218.65px: совпадает с точностью до сотых пикселя
с шириной обычной кнопки в ряду из трёх (218.67px), т.е. ведёт себя ровно как
предписано. Полный набор проверок (20 функциональных/конкурентных + 2
скриншотных прогона) — без регрессий.

**Блокировка кнопок прошлых раундов диалога.** Отдельная находка пользователя:
после каждого нового раунда диалога кнопки **предыдущих** сообщений
оставались кликабельными — должны быть активны только под самым последним
сообщением. Причина: `setLoading(false)` после каждого ответа сервера
включал обратно **все** кнопки на странице (`document.querySelectorAll(".turn__buttons .btn")`),
а не только текущие.

**Исправление:** добавлена явная модель «активного интерактивного блока»
(`activeInteractive` в `script.js`) — при рендере нового сообщения
(`addBotTurn`) элементы предыдущего активного блока (кнопки, поля, textarea —
включая незавершённую форму обратной связи или табы карточки услуги)
блокируются навсегда через `lockActiveInteractive()`, не временно на время
запроса. Вызывается в начале `sendInput()` — значит, срабатывает как на клик
по кнопке, так и на свободный текстовый ввод через форму. `setLoading()`
больше не трогает кнопки сообщений вообще — только хедер и поле ввода.
Правило зафиксировано как кросс-экранное в `docs/bot-ux-flow.md`, раздел 1 —
касается и будущего экрана «ИИ-консультант».

**Проверка (`playwright`, реальные клики, не чтение кода):**
- Раунд 1 (главный экран) → клик по услуге → раунд 1 заблокирован, раунд 2 (карточка) активен.
- Клик по табу → раунд 2 заблокирован, раунд 3 (с активным табом) активен.
- Свободный текстовый ввод (не клик по кнопке) на шаге визарда — тоже блокирует предыдущий раунд.
- Форма обратной связи с ошибкой валидации по-прежнему остаётся интерактивной для повторной попытки в рамках **того же** раунда (не задета новым механизмом, т.к. её локальный retry не проходит через `sendInput`).

Полный набор из 20 функциональных/конкурентных тестов + скриншотные прогоны — без регрессий.
