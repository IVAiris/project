# Plan-bot-flow.md — Фаза «Обычный бот» (`bot_flow.py`)

## 0. Контекст

Тип проекта: учебный (24-часовой MVP «ЮрСправочник»). Уровень плана: **micro** — покрывает одну фазу из `project_plan_24h.md` («3:00–5:30 Обычный бот»), не весь проект.

**Предыдущий слой:** `docs/archive/Plan-sqlite.md` («SQLite», закрыт) — `db.py` готов: `init_db`, `insert_lead`, `insert_feedback`, каждая функция сама открывает/закрывает соединение, `status`/`created_at` вычисляются внутри. Документация (`spec.md`, `docs/bot-ux-flow.md`) актуализирована под утверждённый макет.

**Следующий слой:** «Web UI» (5:30–8:30, `project_plan_24h.md`) — HTTP-роуты FastAPI, `session_id`, рендер экранов (аккордеон FAQ, табы карточки услуги). Этот план **не строит** HTTP-слой и не решает, как визуально рисуется аккордеон/табы — только логику состояний и данных, которые Web UI потом будет дёргать и отображать.

## 1. Статус

Приоритет: высокий — блокирует Web UI (следующая фаза вызывает функции этого модуля из HTTP-роутов) и AI-сценарии (использует тот же `db.py`, тот же формат `contact`). Текущее состояние: не начато, `bot_flow.py` в репозитории нет. Секреты не участвуют. Источник контекста: `docs/bot-ux-flow.md` (разделы 3, 5, 8 — шаги, поля, валидация), `knowledge/services.md`/`faq.md` (контент), `db.py` (контракт `insert_lead`/`insert_feedback`), `urok.md` (Фаза 2, критерии приёмки).

## 1.1 Целевой сценарий

Разработчик (ведущий эту фазу) запускает `python bot_flow.py` локально → self-test проходит весь путь «Оставить заявку» программно (выбор услуги → описание задачи → имя → email → подтверждение → запись в `leads`) и весь путь «Обратная связь» (имя → email → отзыв → запись в `feedback`), а также запрашивает каталог услуг и FAQ → печатает результат каждого шага → разработчик видит в stdout, что весь bot-flow работает без обращения к AI Studio API и без HTTP-слоя. Реальный конечный пользователь увидит эти же сценарии позже, через Web UI (следующая фаза), который будет вызывать те же функции.

## 2. Требования к результату

**Что должно получиться:** `bot_flow.py` в `BOT/project/` — каталог услуг и FAQ (хардкод коротких текстов), state-machine для «Оставить заявку» и «Обратная связь» в виде чистых функций (без HTTP), валидация полей по правилам `docs/bot-ux-flow.md`, вызов `db.insert_lead`/`db.insert_feedback` при подтверждении, self-test блок.

**Явные ограничения (что не делаем в этом плане):**
- Не создаём HTTP-роуты, `session_id`, FastAPI-приложение — это следующий слой (Web UI).
- Не реализуем `agent/tools.py`, не вызываем `agent_runtime.py`/`ai_client.py` — bot-flow работает без LLM по определению (`spec.md`, раздел 5).
- Не решаем, как визуально рендерится аккордеон FAQ или табы карточки услуги (`design-decisions.md`, разделы 5 и 7) — это Web UI. Этот план только готовит данные (какой текст показать), не разметку/CSS/HTML.
- Не парсим `knowledge/services.md`/`faq.md` во время выполнения — короткие тексты для bot-flow хардкодятся в Python отдельно от `knowledge/` (решено 2026-08-30); `knowledge/*.md` остаются источником для `search_knowledge` ИИ-консультанта, не трогаются в этом плане, кроме уже внесённого прямого дополнения — срок предоставления результата для услуг 2 и 3 (3 и 14 рабочих дней соответственно, зафиксировано пользователем 2026-08-30).
- Не реализуем отдельную форму редактирования полей черновика — только предопределённые ветки `"refine"` (одно поле) и `"back"` (полный сброс), см. раздел 2. Свободное редактирование произвольного поля черновика (аналог формы) — не входит в MVP ни для bot-flow, ни для AI-черновика (`docs/bot-ux-flow.md`, раздел 11).

**Файлы, разрешённые к изменению:** `BOT/project/bot_flow.py` (новый), `BOT/project/project_plan_24h.md` (чек-лист по факту), `BOT/project/README.md` (упомянуть `bot_flow.py` в слое Backend/Interface, если потребуется).

**Снимок модели данных и состояний:**

*Каталог услуг* (константа `SERVICES`, хардкод по мотивам `knowledge/services.md`/`README.md`, короткие фразы — не полный юридический текст). Поле `description` обязательно — прямое требование `urok.md` (Фаза 2, критерий «Каталог содержит 3-5 услуг **с описанием**»), в предыдущей версии этого снимка было пропущено:

| `key` | `name` | `description` (что покрывает услуга) | `deadline` (Регламентный срок) | `result` (Ожидаемый результат) |
|---|---|---|---|---|
| `contracts` | Согласование договоров | «Порядок согласования договора в компании, обязательные (существенные) условия, которые должны быть в документе» | «не более 1 рабочего дня на каждом этапе визирования» | «Разъяснение порядка согласования и перечня обязательных условий договора» |
| `pdn` | 152-ФЗ (персональные данные) | «Разъяснения по 152-ФЗ о персональных данных в понятной формулировке» | «до 3 рабочих дней» | «Ответ с цитатой нормы закона и пояснением простыми словами» |
| `deals` | Согласование сделок | «Когда сделка подлежит согласованию по корпоративным документам, что готовить для принятия решения» | «до 14 рабочих дней» | «Разъяснение, требуется ли корпоративное согласование, и что подготовить» |

*FAQ* (константа `FAQ_CATEGORIES`, хардкод по мотивам `knowledge/faq.md`, 4 исходные категории — не аккордеон-ремаппинг из `design-decisions.md` §7, это решение Web UI-фазы): `"Услуги"`, `"SLA, сроки и приоритет обращения"`, `"Формат работы"`, `"Правила и контакты"` — каждая с 2–3 короткими Q/A-парами из `knowledge/faq.md`.

*Состояние диалога* (`flow_state`, часть in-memory сессии из `spec.md` раздел 5 — этот план определяет форму `flow_state`, не саму сессию/HTTP):
```
flow_state = {
    "step": None | "lead_service" | "lead_problem" | "lead_name" | "lead_email" | "lead_confirm"
             | "feedback_name" | "feedback_email" | "feedback_message",
    "data": {
        "service": str | None,       # ключ из SERVICES
        "problem_text": str | None,
        "contact_name": str | None,
        "contact_email": str | None,
        "feedback_message": str | None,
    },
}
```
`step = None` — вне какого-либо сценария (главное меню). `data` накапливается по мере ввода и очищается при завершении (успех/отмена).

**Функции-контракты** (чистые, без побочных эффектов кроме явного вызова `db.insert_lead`/`db.insert_feedback` на шаге подтверждения; принимают и возвращают `flow_state` — не хранят состояние сами, хранение — забота Web UI/сессии следующей фазы):

- `get_services() -> list[dict]` — возвращает `SERVICES`.
- `get_service_card(service_key: str) -> dict` — одна запись `SERVICES` или `ToolError`-подобное исключение при неизвестном ключе (использовать `ValueError`, не заимствовать `ToolError` из `agent_runtime.py` — это разные слои).
- `get_faq() -> dict` — возвращает `FAQ_CATEGORIES`.
- `handle_unknown_input() -> str` — вызывается, когда `step is None` (пользователь вне какого-либо сценария) и пришёл текст, не совпадающий ни с одной командой главного меню; возвращает дружелюбное сообщение с подсказкой открыть «Услуги», «FAQ», «Оставить заявку», «Обратная связь» — закрывает критерий `urok.md` «Неизвестный ввод не ломает сценарий» для случая вне активного сценария (внутри сценария это закрывает `handle_lead_input`/`handle_feedback_input` через ветку невалидного ввода).
- `start_lead_flow(service_key: str | None) -> flow_state` — если `service_key` передан (вход через карточку услуги — `docs/bot-ux-flow.md`, раздел 3), сразу переводит на шаг `"lead_problem"`; если `None` (вход не через карточку) — шаг `"lead_service"`.
- `handle_lead_input(state: flow_state, session_id: str, user_input: str) -> tuple[flow_state, str]` — принимает ввод, валидирует по правилу текущего шага (`docs/bot-ux-flow.md`, раздел 5: услуга — один из 3 ключей; описание — не пустое; имя — ≥2 символов; email — формат). На шаге `"lead_confirm"` — `user_input` один из трёх токенов, названных по реальным кнопкам экрана (не заимствованных из экрана ИИ-консультанта):
  - `"submit"` (кнопка «Оставить заявку») — собирает `contact = f"{name} | {email}"`, вызывает `db.insert_lead(session_id, source="bot_flow", service=..., contact=..., problem_text=..., agent_summary=None, missing_info=None)`, формирует финальное сообщение с `id` («Ей присвоен номер {id}» — `docs/bot-ux-flow.md`, раздел 5), сбрасывает `data`, `step=None`.
  - `"refine"` (кнопка «Уточнить вопрос», решено 2026-08-30) — возвращает на шаг `"lead_problem"`, сохраняя `service`/`contact_name`/`contact_email` в `data`; изменяется только `problem_text`.
  - `"back"` (кнопка «Вернуться на предыдущий экран», решено 2026-08-30 — полный сброс, не частичный) — полностью очищает `data`, `step=None`, `db.insert_lead` не вызывается.

  На невалидном вводе (вне `"lead_confirm"`) — возвращает то же состояние (шаг не продвигается) и сообщение об ошибке, конкретное для этого поля.
- `start_feedback_flow() -> flow_state` — шаг `"feedback_name"`.
- `handle_feedback_input(state: flow_state, session_id: str, user_input: str) -> tuple[flow_state, str]` — тот же паттерн валидации/накопления, на последнем шаге вызывает `db.insert_feedback(...)`, сбрасывает `data` **и** `step` (`step=None`) — симметрично `"submit"` в lead-flow, иначе повторный вызов после завершения останется в шаге `"feedback_message"` с уже пустыми данными.

**Проверка общего ресурса:** не создаётся новых общих ресурсов (портов, файлов) — только новый модуль, использующий уже существующий `db.py`.

## 4. Прямые зависимости и проверки

- Источник истины по шагам/валидации/порядку полей: `docs/bot-ux-flow.md`, разделы 3, 5, 8 (не дублируется в коде комментариями сверх необходимого).
- Источник истины по контракту `db.py`: `docs/archive/Plan-sqlite.md` — `insert_lead`/`insert_feedback` самодостаточны, `bot_flow.py` не открывает свои соединения к БД.
- Источник истины по коротким текстам каталога/FAQ: `knowledge/services.md`/`faq.md` — `bot_flow.py` хранит собственные короткие версии, отдельные от них (решение 2026-08-30); при изменении сроков/описаний в `knowledge/*.md` нужно вручную синхронизировать `SERVICES`/`FAQ_CATEGORIES` в `bot_flow.py` — это ручной процесс, не автоматический, задокументировать как известное ограничение, не техдолг.
- **Смешение сценариев «Пробел №3» закрыто макетом:** вход через карточку услуги передаёт `service_key` в `start_lead_flow()`, пропуская шаг выбора услуги — реализация должна поддерживать оба входа (с `service_key` и без), не только один.
- Типовая ошибка всей фазы: реализовать валидацию полей внутри `db.py` вместо `bot_flow.py` — по контракту `Plan-sqlite.md` `db.py` валидирует только `NOT NULL`, содержательная валидация (формат email, длина имени) — обязанность этого модуля.
- **Найденный и исправленный баг (2026-08-30): `handle_lead_input`/`handle_feedback_input` изначально мутировали входной `state["data"]` на месте**, хотя раздел 2 этого плана прямо называет их «чистыми функциями». Обнаружено независимой проверкой (`copy.deepcopy` состояния до/после вызова), не самим self-test. Исправлено: обе функции теперь делают `data = dict(state["data"])` — работают с копией, не трогают объект, переданный вызывающим кодом. Проверено повторно после фикса: state до вызова побитово равен снимку, self-test и все проверки невалидного ввода прошли без регрессий. Это было бы реальной проблемой для Web UI-фазы, если бы сессия хранила ссылку на предыдущее состояние (например, для отладки/логов).
- **Конкурентный доступ на уровне `bot_flow.py` проверен отдельно от `db.py`.** 25 параллельных потоков, каждый — независимая сессия, полный путь `start_lead_flow → 4×handle_lead_input → submit`: 25/25 успешно, 25 уникальных `session_id` в `leads`, 0 ошибок, 0 смешения данных между сессиями. Это дополнительная проверка сверх той, что уже была сделана для `db.py` (`docs/archive/Plan-sqlite.md`) — подтверждает, что и сам `bot_flow.py` (не только `db.py`) корректно ведёт себя при одновременной работе нескольких сотрудников (`spec.md`, раздел 6).
- **Защита от двойного подтверждения (`spec.md`, раздел 6) — не входит в этот модуль.** Функции `handle_lead_input`/`handle_feedback_input` в этой фазе чистые и идемпотентность не гарантируют: если вызывающий код (Web UI, следующая фаза) повторно вызовет `handle_lead_input` с действием `"submit"` на уже устаревшем объекте `flow_state` (вместо актуального, полученного после первого `"submit"`), будет создана вторая запись в `leads`. Guard на этот случай — обязанность слоя сессии Web UI (frontend блокирует кнопку, backend не переиспользует состояние после успешного сохранения), не `bot_flow.py`. Явно зафиксировано, чтобы не потерялось при переходе к следующей фазе.
