# Логика бота для эскиза интерфейса — ЮрСправочник

Свод зафиксированных решений из `spec.md`, `README.md`, `knowledge/*.md`, `urok.md` —
для отрисовки эскиза экранов. Раздел «Пробелы» в конце — то, что для эскиза
понадобится, но нигде не решено; додумывать не стал, только подсветил.

> **Статус актуализации (2026-08-30, фаза Web UI).** Реализация `app.py`/
> `bot_flow.py`/`static/` сверена не только с текстом этого документа, но и
> пиксель-в-пиксель с `docs/maket/` — сверка вскрыла два расхождения, которых
> не было видно по одному тексту: кнопка «Вернуться на предыдущий экран»
> обязана быть на **каждом** шаге визарда заявки (раздел 5), а «Обратная
> связь» — это **форма** с тремя одновременно видимыми полями (раздел 8), не
> последовательный опрос. Оба раздела ниже обновлены под макет; решение о
> «нет аварийного выхода из визарда», ранее принятое из-за неполного чтения
> текста этого документа без сверки с самими PNG, отменено.

## 1. Общая структура экрана

Один экран web-чата (`urok.md`: «один простой web-интерфейс чата с историей
сообщений, меню и полем ввода»). На экране одновременно присутствуют:
- история сообщений в рамках текущей сессии;
- главное меню;
- поле текстового ввода (доступно всегда, не только внутри ИИ-консультанта).

**Кросс-экранное правило (решено 2026-08-30, обнаружено при проверке Web
UI):** кнопки под сообщением активны только у **самого последнего**
сообщения в ленте. Как только появляется новый раунд диалога — кнопки и
поля предыдущих сообщений (включая уже показанные карточки услуг, табы,
табло FAQ, незавершённые формы) навсегда блокируются, а не остаются
кликабельными «в истории». Правило действует на всех экранах, включая
будущий экран «ИИ-консультант» — не только на уже реализованных.

## 2. Главный экран и хедер (решено 2026-08-30, по макету `docs/maket/`)

**Хедер:** заголовок «ЮрСправочник» + две кнопки справа — **FAQ** и
**Обратная связь**.

**Тело главного экрана:** приветственное сообщение бота оформлено как
чат-сообщение (карточка с текстом, не отдельная статичная секция сайта):
кто бот, чем помогает (кратко перечисляет 3 темы), приглашение выбрать
услугу или написать вопрос ИИ-консультанту. Под сообщением — quick-reply
кнопки с реальными названиями услуг (не «Услуга 1/2/3» — это в макете были
плейсхолдеры): **«Согласование договоров»**, **«152-ФЗ (персональные
данные)»**, **«Согласование сделок»** — и отдельная широкая кнопка
**«Перейти к ИИ-консультанту»**.

**Отдельной видимой кнопки «Оставить заявку» на главном экране нет.**
Раньше в этом разделе было заявлено «пять самостоятельных, одновременно
видимых пунктов» — это неточно, разбор двух формулировок `urok.md` показал
следующее:
- «Что нужно сделать» (Фаза 2, описание работы) действительно перечисляет
  все 5 пунктов поимённо, включая «Оставить заявку».
- «Критерии приёмки этой фазы» (то, по чему реально проверяют) требуют
  мягче: «На главном экране видны основные режимы и поле ввода» — без
  поимённого перечня всех пяти как равноценных кнопок.

Решение: «Оставить заявку» не выведена отдельной кнопкой на главном
экране — она достижима через «Услуги» и через «ИИ-консультант» (два пути
к одному результату, детали — в разделах про соответствующие экраны, не
здесь). Это решение снижает риск при строгом ревью по описательному
тексту фазы, но не исключает его полностью — риск отмечен, не устранён.

**Пробел №1 (компоновка экрана: персистентное меню или conversational
quick-reply) — закрыт.** Макет показывает conversational-стиль: приветствие
как чат-сообщение, кнопки услуг как quick-reply под ним — не персистентная
навигационная панель отдельно от чата.

## 3. Экран «Услуги»

Каталог из 3 предметных услуг (`knowledge/services.md`, `README.md`):

| № | Услуга | Что видит пользователь |
|---|---|---|
| 1 | Консультация о порядке согласования договоров | Обязательные условия договора, этапы согласования по регламенту |
| 2 | Консультация об обработке персональных данных (по 152-ФЗ) | Ответы с цитированием статьи закона + пояснение простыми словами |
| 3 | Получение корпоративного одобрения сделки | Критерии обязательности корпоративного согласования, что готовить, с кем согласовывать |

Bot-flow и ИИ-консультант — единый технический слой поверх этих трёх услуг,
не три разных «под-бота» (`README.md`).

**Карточка услуги** (решено 2026-08-30, по макету
`docs/archive/design-decisions(old).md`, раздел 5) — открывается после выбора конкретной услуги на главном экране
или в разделе «Услуги»: внутри три таба-кнопки, переключающие содержимое
одной и той же карточки — «Регламентный срок», «Ожидаемый результат»,
«Получить услугу» (активная кнопка выделена золотым контуром). Таб
«Получить услугу» ведёт в bot-flow оформления заявки (раздел 5 ниже) с уже
предвыбранной услугой. Возврат — кнопка «Вернуться на предыдущий экран»,
присутствует на каждом шаге сценария.

## 4. Экран «FAQ»

**Вход в экран** — по клику на кнопку «FAQ» в хедере, открывается как
карточка в текущей ленте чата, без сброса истории.

**Структура — аккордеон** (решено 2026-08-30, по макету
`docs/archive/design-decisions(old).md`, раздел 7):

1. **3 кнопки-аккордеона по услугам** («Согласование договоров», «152-ФЗ»,
   «Согласование сделок») — единый шаблон полей при разворачивании: название
   услуги, сроки предоставления результата, как подать заявку (применительно
   к конкретной услуге), что представить для получения услуги.
2. **Отдельная кнопка «Правила и контакты»** — свой набор пунктов: как
   пользоваться ИИ-консультантом, что делать при ошибках ИИ (со ссылкой на
   «Обратную связь»), как подать заявку (общий процесс).

**Осознанное дублирование:** пункт «Как подать заявку» есть и в карточке
услуги, и в «Правилах» — принято сознательно. Поведение аккордеона —
разворачивание текста поверх экрана (оверлей). Навигация — кнопка
«Вернуться на предыдущий экран».

Исходные 4 категории контента (`spec.md`, раздел 5; `knowledge/faq.md`) —
услуги, SLA/сроки/приоритет обращения, формат работы, правила и контакты —
распределены между двумя пунктами структуры аккордеона выше, а не выведены
отдельными четырьмя кнопками.

Пример реального содержимого одной карточки (для реалистичного текста в
эскизе, `knowledge/faq.md`):
> «Сколько времени бот отвечает на вопрос?» → «До 2 минут — зависит от
> сложности обращения и типа консультации.»

## 5. Экран «Оставить заявку» (bot-flow, без LLM)

Пошаговый сценарий (решено 2026-08-30, по макету `docs/maket/`,
`docs/archive/design-decisions(old).md` раздел 5 — порядок полей заменяет более раннюю версию
этого раздела):

```
Шаг 1 → выбрать услугу (карточка услуги на главном экране / «Услуги»,
         те же 3 пункта каталога)
Шаг 2 → описать суть вопроса (с инструкцией про вложение документов —
         папка «Для юридической службы» на диске P:\); валидация «не
         пустой ввод», при ошибке — явное сообщение без сброса шага
Шаг 3 → «Как к Вам обращаться?» — валидация не менее 2 символов
Шаг 4 → корпоративная почта — валидация формата email, без ограничения
         по домену
Шаг 5 → финальная сводка и подтверждение
```

**Кнопка «Вернуться на предыдущий экран» доступна на каждом из шагов 1–4**
(решение пересмотрено 2026-08-30 по сверке с `docs/maket/`, страницы 2–3 — там
эта кнопка нарисована рядом с полем ввода на каждом шаге, не только на
финальной сводке). Нажатие на любом шаге полностью сбрасывает черновик и
возвращает в главное меню — частичного возврата на один шаг назад через эту
кнопку нет (это делает кнопка «Уточнить вопрос» только на финальной сводке,
см. ниже). Более раннее решение «нет аварийного выхода из визарда» было
принято по неполному чтению текста этого документа без сверки с самими
PNG-макетами — отменено.

**Финальная сводка** (лента чата): «От: [Контакт: как обращаться | email]»,
«Тема: [Название услуги]», «Заявка на предоставление консультации по
вопросу: [Инпут вопроса]» — кнопки «Вернуться на предыдущий экран»,
«Уточнить вопрос», «Оставить заявку» (золотой контур как primary-действие).

**Финальное сообщение после подтверждения:** «Ваша заявка направлена в
Юридическую службу. Ей присвоен номер [ID заявки]» — `ID заявки` это
стандартный `id` (SQLite `INTEGER PRIMARY KEY`) поля `leads`, формат и
порядок присвоения — вне UX-документа, см. `spec.md`, раздел 5.

**Формат хранения контакта:** схема `leads` фиксирует `contact` одной колонкой
(`urok.md`, не меняется). Оба поля формы объединяются в единую строку с
фиксированным разделителем: `"{как обращаться} | {email}"` — разделитель
всегда один и тот же, что делает значение надёжно разбираемым при обработке
данных (`" | "` не может появиться в валидном email, а поле «Как обращаться»
не должно содержать этот разделитель).

Работает полностью без ключа/лимита AI Studio. Неизвестный ввод не ломает
сценарий (`urok.md`).

Сохраняется в `leads` с `source = bot_flow`, `status` определяется
автоматически (`new`, если `missing_info` пусто — для bot-flow это всегда так).

## 6. Экран «ИИ-консультант»

**Вход в экран** (решено 2026-08-30, по макету — закрывает п.4 «Пробелов»):
без приветственного сообщения бота. Единственный видимый элемент при входе —
активное поле ввода с плейсхолдером «Задайте Ваш вопрос».

```
Пользователь задаёт вопрос свободным текстом
   ↓
Агент ищет ответ в knowledge/ (search_knowledge / read_knowledge_file)
   ↓
Есть ответ в базе?
   ├── Да → отвечает со ссылкой на материал, при необходимости
   │        задаёт 1–2 уточняющих вопроса
   └── Нет → честно сообщает об этом, предлагает оставить заявку
   ↓
Готов подготовить черновик? → запрашивает контакт теми же двумя полями,
   что и bot-flow («Как обращаться» + email, см. раздел 5) — единообразно
   для обоих сценариев, не берётся из текста диалога
   ↓
Показывает черновик (см. раздел 7)
```

Ограничения, которые должны быть видны в поведении на эскизе (`knowledge/rules.md`,
`agent/soul.md`): не выдумывает факты вне базы; не подменяет консультацию
юриста; при вопросе про `.env`/файлы вне `knowledge/` — отказывает.

**Что происходит с введённым контактом до подтверждения заявки** (уточнение
2026-08-30, по вопросу о хранении):

1. Пользователь вводит имя и email в два поля.
2. Эти значения сразу же — ещё до показа черновика — кладутся во временную
   память сервера для текущего разговора, рядом с остальными частями
   черновика (услуга, описание задачи и т.д.), которые там уже есть.
3. Пользователь видит черновик — в нём отображается и введённый контакт,
   потому что он там уже лежит.
4. Если пользователь нажимает «Отправить заявку» — всё содержимое временной
   памяти (включая контакт) копируется в постоянную базу данных (SQLite),
   появляется реальная строка в таблице `leads`.
5. Если пользователь нажимает «Отмена» — временная память стирается,
   включая контакт, в базу данных ничего не попадает.

## 7. Экран черновика заявки (confirmation flow)

Показывается после того, как ИИ-консультант собрал достаточно данных
(`urok.md`, Фаза 4; `spec.md` раздел 5). Черновик включает:

- подходящая услуга;
- краткое описание задачи;
- контакт (тот, что пользователь сам оставил);
- что уже известно;
- чего не хватает;
- исходное сообщение или короткая выжимка.

Три действия под черновиком:
- **«Отправить заявку»** → `save_confirmed_lead`, `source = ai_consultant`,
  кнопка блокируется сразу по клику до ответа backend (защита от двойного
  подтверждения, `spec.md` раздел 6). После сохранения пользователь видит то
  же финальное сообщение с `ID заявки`, что и в bot-flow (раздел 5).
- **«Изменить»** → возврат к уточнению.
- **«Отмена»** → черновик не сохраняется, записи в `leads` не создаётся.

## 8. Экран «Обратная связь»

**Пересмотрено 2026-08-30 по сверке с `docs/maket/`, страница 5.** Ранее эта
секция описывала последовательный опрос по одному полю за раз (как bot-flow
заявки) — это была ошибка чтения текстового `docs/archive/design-decisions(old).md`
без сверки с самим макетом. На макете это **веб-форма**: три поля показаны
**одновременно**, с общей кнопкой «Отправить»:
1. «Укажите, как к Вам обращаться» — не менее 2 символов.
2. «Укажите Вашу эл. почту» — валидация формата email.
3. «Введите Ваш отзыв здесь» — не пустой ввод.

Проверки такие же, как у полей bot-flow заявки, но выполняются **все сразу**
по клику «Отправить», не по одной на каждый Enter. Ошибка показывается
текстом под конкретным полем, остальные поля не затрагиваются.

Схема `feedback` расширена под три поля отдельными колонками (не
конкатенация в одну строку, в отличие от `contact` в `leads`) — точная схема
таблицы, см. `spec.md`, раздел 5.

**Ветка частичной ошибки:** если хотя бы одно поле не проходит проверку —
под каждым невалидным полем появляется текст ошибки, уже введённые
корректные значения в других полях не стираются («История заполнения на
странице сохраняется, не сбрасывается» — аннотация макета), кнопка
«Отправить» остаётся доступной для повторной попытки без потери данных.

**Успешное завершение:** форма исчезает, вместо неё — сообщение «Ваш отзыв
направлен и будет рассмотрен.»

Без привязки к услуге. Сохраняется отдельно от `leads`, не смешивается с
заявками. Навигация — кнопка «Вернуться на предыдущий экран» внутри формы.

## 9. Данные, которые бот никогда не запрашивает

(`knowledge/rules.md`, `spec.md` раздел 5) — не должно появляться ни в одной
форме на эскизе: паспортные данные, номера карт, содержимое `.env`, системные
секреты, любые сведения не по теме трёх услуг каталога.

## 10. Состояние ошибки / недоступности ИИ

Если AI Studio API недоступен в середине сессии (`spec.md`, раздел 6) —
пользователь видит дружелюбное сообщение о временной недоступности с
предложением воспользоваться обычным меню; история диалога не сбрасывается.
Bot-flow при этом продолжает работать (не зависит от AI Studio).

## 11. Решено в ходе разбора пробелов (2026-08-30)

**Поведение кнопки «Изменить» в черновике заявки.** Возвращает пользователя в
свободный чат для уточнения текстом — черновик формирует ИИ по диалогу, не
статичная форма, поэтому естественно уточнять его тем же способом. Отдельный
UI редактирования полей черновика не реализуется в MVP.

> **Точка роста (не MVP):** редактирование черновика через отдельную форму
> полей вместо возврата в чат. Не реализуется — увеличило бы scope без
> требования `urok.md`.

**Формат поля «контакт»** — закрыто, см. раздел 5 выше: два поля формы («Как
обращаться» + email с валидацией), объединяются в одну строку `contact` через
фиксированный разделитель `" | "`.

**Истёкшая/ненайденная сессия** (backend не находит активную сессию по
`session_id`, например после перезапуска runtime) — тихий сброс без
отдельного экрана-предупреждения: backend создаёт новую сессию молча, диалог
начинается заново. Обоснование: `spec.md` прямо называет потерю активной
сессии «допустимой» — это не сбой, а принятый случай, специальный UI под него
не нужен. Не путать с разделом 10 (это про недоступность AI Studio API, а не
про истечение сессии — разные ситуации).
