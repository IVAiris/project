# CLAUDE.md — ЮрСправочник

Проект: учебный MVP чат-бота с ИИ-консультантом (24-часовой спринт). Файл настраивает
режим работы ИИ-помощника именно в этом репозитории и заменяет `AGENTS.md` из
эталонного цикла урока `Spec → Plan → AGENTS.md → Code → Check → README`.

## 1. Что читать первым

Часть источников физически лежит **вне** `project/` (корня этого репозитория) —
это исходные материалы урока, не часть git-репозитория:

1. `../urok.md` — исходное задание и жёсткие технические границы. Высший
   приоритет: при любом конфликте с другими документами побеждает `urok.md`.
2. `spec.md` (этот репозиторий) — продуктовые решения проекта: цели, не-цели,
   функциональные требования, сессии, риски. Источник продуктовой логики —
   именно этот файл, не `README.md`.
3. `README.md` — легенда, каталог услуг, структура меню, план по слоям.
4. `project_plan_24h.md` — почасовой макро-план всего проекта.
5. Активный `Plan-*.md` в корне `project/` — микро-план текущей фазы, единственный
   источник конкретных шагов текущей работы. Сейчас это `Plan-ai-scenarios.md`
   — объединённые фазы «AI-сценарии» + «Черновик и подтверждение»
   (`10:00–14:00`, `project_plan_24h.md`). Закрытые планы переносятся в
   `docs/archive/` (`Plan-runtime.md` — «Основа runtime», `Plan-sqlite.md`
   — «SQLite», `Plan-bot-flow.md` — «Обычный бот», `Plan-web-ui.md` —
   «Web UI», `Plan-tools.md` — «Безопасные tools») и больше не активны,
   даже если это единственный `Plan-*.md`, видимый в репозитории.
6. `knowledge/services.md`, `faq.md`, `rules.md` — контент базы знаний бота
   (не инструкция для ИИ-помощника, это данные для будущего `search_knowledge`).
7. `../ai_studio_api_notes.md`, `../agent-py.md` — технический эталон паттерна
   AI Studio API и agent runtime, который проект обязан переносить «почти без
   изменений» (см. `project_plan_24h.md`, раздел «Что перенести без изменений»).
8. `docs/bot-ux-flow.md` — источник истины по экранам, меню, флоу и UX-решениям
   (см. раздел 2 ниже); нужен для любой задачи, касающейся интерфейса бота.

## 2. Источник продуктовых правил

Разделение источников истины (зафиксировано 2026-08-30):

| Тип факта | Источник истины | Остальные документы |
|---|---|---|
| Данные/схема, сессии, tools, нефункциональные требования, риски | `spec.md` | ссылаются, не повторяют |
| Экраны, меню, флоу, формат полей, кнопки, UX-решения | `docs/bot-ux-flow.md` | `spec.md`/`README.md` ссылаются, не повторяют |
| Контент для самого бота (регламенты, эскалация, справочные факты) | `knowledge/rules.md` | не дублируется человеческими доками, но должен быть непротиворечив |

`README.md` описывает то же самое для читателя проекта, но при расхождении
актуальным считается `spec.md` (для UX — `docs/bot-ux-flow.md`); оба
обновляются первыми при любом решении, `README.md` — вторым.

## 3. Разрешённый стек

По `requirements.txt`: `fastapi`, `uvicorn`, `openai`, `python-dotenv==1.2.2`.
Python 3.13.x, `.venv`. Хранилище — `sqlite3` (стандартная библиотека, без
доп. зависимостей). Frontend — статические HTML/CSS/JS без фреймворка
(зафиксировано в `spec.md`, раздел 7). AI-клиент — только
`client.chat.completions.create()`, не `responses.create()` (см.
`ai_studio_api_notes.md`).

## 4. Что нельзя добавлять без явной задачи

**Запрет расширения scope** — ничего из раздела «Не-цели» `spec.md` не
реализуется даже частично без нового явного согласования с пользователем:
RAG/embeddings/векторная БД, авторизация/роли/личный кабинет, интеграции с
Telegram/СЭД/1С/e-mail, cookie-session/Redis, реальная отправка заявки во
внешнюю систему, загрузка и анализ файлов пользователя.

Новая зависимость (пакет, фреймворк, внешний сервис) не добавляется в
`requirements.txt` без отдельного подтверждения пользователем — даже если она
кажется полезной или тривиальной.

**Любой запрос на согласование расширения scope или новой зависимости
оформляется ЗАГЛАВНЫМИ БУКВАМИ, отдельной строкой** (например: «ТРЕБУЕТСЯ
СОГЛАСОВАНИЕ: добавить пакет X» / «ТРЕБУЕТСЯ СОГЛАСОВАНИЕ: расширить scope за
счёт Y») — чтобы такой запрос не терялся на фоне обычного текста ответа.

**Уже зафиксированные инженерные решения (не пересматривать без причины):**
- `MAX_STEPS = 6` — точное значение из `agent-py.md`, не увеличивать
  автоматически при зацикливании (сначала искать причину).
- `ToolError` определяется в `agent_runtime.py`; `agent/tools.py` импортирует
  его оттуда — не в обратном направлении (иначе кольцевой импорт).
- Логи agent loop — только теги `[task]`, `[loop]`, `[tool]`, `[refusal]`
  (формат из `agent-py.md:990-1036`), без секретов и лишних персональных
  данных.
- `.env` читается через `PROJECT_ROOT`-относительный путь, не через
  `load_dotenv()` без аргументов.
- `session_id` генерируется backend, хранится в памяти процесса — не в SQLite
  (см. `spec.md`, раздел 5).
- `db.py`: каждая функция (`init_db`, `insert_lead`, `insert_feedback`) сама
  открывает и закрывает соединение через `get_connection(db_path=DB_PATH)` —
  соединение никогда не кэшируется на уровне модуля (нужно для безопасного
  вызова из будущего threadpool FastAPI). `get_connection()` включает
  `row_factory = sqlite3.Row`.
- `leads.id` — обычный SQLite `INTEGER PRIMARY KEY` (совпадает с `rowid`),
  отдельный счётчик не заводится.
- `created_at` в `leads`/`feedback` — ISO-8601 строка, генерируется в Python
  (`datetime.now().isoformat()`), не `CURRENT_TIMESTAMP` СУБД.
- Действия визарда bot-flow-заявки — строго `"submit"`/`"refine"`/`"back"`
  (по реальным кнопкам `docs/bot-ux-flow.md`, раздел 5), **не**
  `"confirm"/"edit"/"cancel"` — это термины другого экрана (черновик
  ИИ-консультанта), их нельзя смешивать. `"back"` обрабатывается в самом
  начале `bot_flow.handle_lead_input()` (до диспетчеризации по `step`) и
  доступен на **каждом** шаге визарда, не только на финальном подтверждении
  (пересмотрено 2026-08-30 по сверке с `docs/maket/` — исходное решение «нет
  аварийного выхода» было принято без сверки с самими PNG-макетами).
- «Обратная связь» — одноразовая отправка формы (`bot_flow.submit_feedback(session_id, contact_name, contact_email, message_text) -> (ok, errors)`),
  не пошаговый автомат — валидирует все три поля сразу, возвращает словарь
  ошибок по каждому. `start_feedback_flow`/`handle_feedback_input` (пошаговый
  вариант) удалены из `bot_flow.py` 2026-08-30 по той же сверке с макетом.
  `app.py` не хранит `mode="feedback_flow"` в сессии — форма шлётся одним
  запросом `input="feedback_submit"` с телом `payload`.
- Frontend: кнопки/поля активны только у самого последнего сообщения в
  ленте — как только рендерится новый раунд, элементы предыдущего блокируются
  навсегда (`static/script.js`, `lockActiveInteractive()`), не временно на
  время запроса. Кнопка «Вернуться на предыдущий экран» — класс `.btn--back`,
  ограничена ~1/3 ширины строки (`flex: 0 1 calc(...)`), не растягивается
  наравне с соседними кнопками — см. `static/style.css`.
- Короткие тексты каталога услуг/FAQ в `bot_flow.py` хардкодятся в Python
  отдельно от `knowledge/*.md` (решение 2026-08-30) — `knowledge/*.md`
  остаётся источником только для `search_knowledge` ИИ-консультанта; при
  изменении сроков/описаний в `knowledge/*.md` требуется вручную
  синхронизировать `bot_flow.py`.
- `call_tool`/`run_agent` в `agent_runtime.py` принимают явные параметры
  `session_id`/`session` от вызывающего кода (`app.py`) — расширение
  сигнатуры терминального урока (там был однопользовательский CLI без
  сессий, источник не даёт готового паттерна для web-сессий); решение
  проекта, обоснование — `spec.md`, раздел 5.
- `save_confirmed_lead` не входит в JSON-схему `tools`, которую видит модель
  в agent loop (`KNOWN_TOOLS` в `agent_runtime.py` — только
  `search_knowledge`, `read_knowledge_file`, `prepare_lead_draft`) —
  вызывается `app.py` напрямую как обычная функция при клике «Отправить
  заявку», тем же паттерном, что `submit`/`refine`/`back` в `bot_flow.py` и
  `feedback_submit`. Мотивированное обоснование — `spec.md`, раздел 5.
- `prepare_lead_draft` не принимает `contact` как аргумент модели — контакт
  не парсится моделью из свободного текста, а собирается отдельным
  структурным под-шагом backend; backend дописывает `contact` в
  `session["lead_draft"]` до показа черновика пользователю.
- Session-режимы: `"ai_consultant"`, `"ai_confirm_problem"`, `"ai_edit_problem"`,
  `"ai_contact_name"`, `"ai_contact_email"`, `"ai_lead_confirm"` — плоские
  строковые значения `session["mode"]` (`Plan-ai-scenarios.md`).
- `session["ai_history"]` инициализируется как `[]`, не `None`, при входе в
  режим `ai_consultant` — `agent_runtime._get_messages` мутирует список на
  месте только если это уже список; `None` теряет историю после первого
  же ответа модели.
- Эскалация вызывает `prepare_lead_draft` через синтетический служебный
  ход в `run_agent`, не backend-вызовом в обход модели — контракт см.
  `spec.md`, раздел 5. Работа модели на этом заканчивается: контакт,
  черновик и сохранение — без обращения к модели.
- `bot_flow.py`: `EMAIL_RE`/`validate_contact_name` — новые аддитивные
  функции для контакта ИИ-консультанта, не переписывают существующие
  `handle_lead_input`/`submit_feedback`.
- «Изменить» на черновике ИИ-консультанта не сбрасывает `session["ai_history"]`
  (в отличие от входа в режим с главного меню) — см. `docs/bot-ux-flow.md`,
  раздел 11.
- `search_knowledge` — двухслойный поиск: точная фраза целиком (приоритет),
  при неудаче — по одному, самому длинному слову запроса с грубой обрезкой
  окончания (`MAX_STEM_STRIP=3`), не AND по всем словам и не эмбеддинги —
  полная история решения и отклонённые варианты см. `Plan-ai-scenarios.md`,
  Шаг 5.1.

## 5. Поведение при нехватке контекста

Не додумывать отсутствующие решения. При недостатке вводных — задавать
пользователю точный уточняющий вопрос и ждать ответа, а не выбирать вариант
самостоятельно. Это касается и мелких технических деталей (например, порядок
полей, формат сообщения об ошибке), и архитектурных решений.

## 6. Как определять проверки после изменений

В репозитории нет автоматических тестов, CI или линтера — `requirements.txt`
не содержит `pytest`/`ruff`/аналогов, конфигурации CI нет. Поэтому после
любого изменения:
1. Смотреть «Проверка» и «Ошибки» у соответствующего шага в активном
   `Plan-*.md` — это единственный источник конкретных критериев для текущей
   задачи.
2. Выполнять ручную проверку описанного там сценария (например,
   `python agent_runtime.py` для self-test блока).
3. Если позже появятся тесты/CI/линтер — обновить этот пункт, ссылаясь на
   конкретные команды из репозитория, а не изобретать проверки заново.
4. **Проверки в `Plan-*.md` должны быть реальными и действенными, не только
   синтетическими.** Self-test, написанный в рамках того же шага (тем же
   циклом работы), может унаследовать те же слепые пятна, что и сам код —
   его прохождение не равно факту работоспособности. Прецедент: self-test
   `bot_flow.py` не поймал мутацию входного `state` на месте — баг вскрылся
   только отдельной независимой проверкой (`copy.deepcopy` состояния до/после
   вызова), написанной не как часть self-test. Поэтому по каждому шагу, где
   это применимо, — после self-test проводить хотя бы одну независимую
   проверку (граничные случаи, невалидный ввод, конкурентный доступ, побочные
   эффекты/чистота функций) сразу после выполнения шага, не откладывая на
   отдельную фазу «Check» в конце. Результат — в поле «Проверка» и, при
   находке, в «Ошибки» соответствующего шага `Plan-*.md`. Сюда же — все
   новые ветки диспетчеризации (режимы, значения кнопок), добавленные
   шагом, не только сценарий, ради которого шаг делался: правка входа в
   `ai_consultant` (`Plan-ai-scenarios.md`, Шаг 3) сломала кнопку
   «Вернуться» в остальных ситуациях, не проверенных сразу.
5. HTTP-проверки через реально запущенный `uvicorn` — с изолированной БД
   (подменять `db.DB_PATH`/`db.insert_lead` как в self-test `bot_flow.py`),
   не с `data/bot.sqlite3` — иначе тестовые записи попадают в боевые данные.

## 7. Рабочие правила

- **Секреты:** реальный `.env` никогда не читается, не печатается, не
  цитируется ИИ-помощником целиком или частично. В коде и логах — только
  `os.getenv("ИМЯ_ПЕРЕМЕННОЙ")`, никогда не hardcoded значение. Проверка
  наличия ключа выполняется через обёрнутый скрипт, который не печатает сам
  ключ (по образцу `test_connection.py`).
- **Зоны, которые не трогать без отдельного запроса:** файлы вне `project/`
  (`../urok.md`, `../agent-py.md` и другие материалы урока — это исходники
  для чтения, не для правки); `knowledge/*.md` — контент, зафиксированный
  пользователем как продуктовые решения, правится только по прямому запросу;
  `.venv/` и `data/*.sqlite3*` — генерируемые артефакты, не редактируются
  вручную и не коммитятся.
- **Обязательное обновление документации при изменениях:** любое решение,
  меняющее архитектуру, контракт данных или scope, сразу отражается в
  `spec.md` (и в `README.md`, если оно касается пользовательского сценария)
  в том же цикле работы — не откладывается на потом.
- При правке уже существующего текста или уже протестированного кода —
  diff обязан показывать только сам замысел правки: явные формулировки-
  запреты и уже работающая логика не пропадают и не переписываются
  попутно (дважды случалось в этой сессии — терялся текст запрета в
  `spec.md`, предлагалась переработка тестового `bot_flow.py`).
- **Перед изменениями** — показать пользователю список файлов, которые будут
  затронуты, план правок и команды (если они нужны). **После изменений** —
  обновить статус, «Факт выполнения» и «Ошибки» соответствующего шага в
  активном `Plan-*.md` (по образцу правила из `agent-py_summery.md`,
  `reference_bot_summery.md`, `summery_uroka.md`).
- Один активный пункт `Plan-*.md` в работе за раз; после выполнения — сразу
  заполнять «Факт выполнения» и «Ошибки» (конкретный факт или «нет»), не
  оставлять шаг в подвешенном состоянии.
- **Актуализация `CLAUDE.md`** — отдельный, самостоятельно согласуемый шаг
  цикла `spec.md → Plan.md → CLAUDE.md → Code → Check → README.md`, а не
  попутная правка вместе с другими файлами. Выполняется только после того,
  как соответствующие изменения уже зафиксированы в `spec.md` и в активном
  `Plan-*.md`. Черновик правки `CLAUDE.md` показывается пользователю на
  согласование до записи файла — даже если правка выглядит мелкой (например,
  исправление устаревшей ссылки на архивный план).
- Любое действие, создающее/меняющее/удаляющее файл или устанавливающее
  пакет, показывается пользователю для подтверждения до выполнения.
