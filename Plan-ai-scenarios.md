# (10:00–14:00, `project_plan_24h.md`, два тайм-слота объединены — см. раздел 0)

## 0. Контекст

Тип проекта: учебный MVP (24-часовой спринт), цикл `spec.md → Plan.md →
CLAUDE.md → Code → Check → README.md`.

Уровень плана: **micro-Plan.md**, но по решению, принятому при составлении
этого плана (не додумано молча — описано в разделе 1 как самостоятельное
решение на согласование), объединяет **два** тайм-слота почасовой таблицы:
«10:00–12:30 AI-сценарии» и «12:30–14:00 Черновик и подтверждение».
Причина объединения — они образуют один непрерывный диалоговый маршрут
внутри `app.py` (вопрос → эскалация → уточнение текста → контакт →
финальный черновик → сохранение); честно разбить их на два отдельных
Plan.md означало бы после первого из них оставить веб-чат в
незавершённом промежуточном состоянии (экран, ведущий в ещё
нереализованный режим сессии) — это хуже, чем один более длинный, но
цельный цикл. Прецедент честного объединения фаз уже был обратный —
`Plan-tools.md` сознательно НЕ трогал `app.py`, потому что там граница
чистая (чистый backend-модуль); здесь граница нечистая (один непрерывный
UI-сценарий), поэтому решение симметрично другое.

Связь с другими планами: предыдущий слой — `Plan-tools.md` (закрыт,
`agent/tools.py` и `agent_runtime.py` готовы и проверены). Следующий слой
— «Тестирование» (14:00–16:00), для которого micro-Plan не заводился по
традиции этого проекта (см. `project_plan_24h.md` — там ручная проверка
идёт по чек-листу самого почасового плана).

**Самостоятельно принятые решения при составлении этого плана** (по
прямому запросу пользователя — решить и коротко описать для его
рассмотрения, не додумывать молча в код):

1. **Объединение двух тайм-слотов в один план** — обоснование выше.
2. **Session-режимы** — новый набор значений `session["mode"]`:
   `"ai_consultant"` (свободный чат) → `"ai_confirm_problem"` (предпросмотр
   текста запроса) → `"ai_edit_problem"` (редактирование, один ввод) →
   `"ai_contact_name"` → `"ai_contact_email"` → `"ai_lead_confirm"`
   (финальный черновик). Выбран плоский набор строк по образцу уже
   существующего `"lead_flow"`/`"main_menu"`, а не вложенный
   `flow_state`-словарь (как в `bot_flow.py`) — потому что здесь нет
   повторного использования одной и той же функции-обработчика на разных
   шагах, каждый шаг — отдельный, простой обработчик.
3. **`session["ai_history"]` — список, не `None`, сразу при входе в режим.**
   Технически важная деталь (не предпочтение): `agent_runtime._get_messages`
   мутирует переданный список **на месте** (`.append`/`.insert`) только
   если это уже список; если передать `None`, функция создаёт новый список
   **внутри себя**, а `run_agent` не возвращает его наружу — история
   потерялась бы после первого же ответа. Поэтому при входе в режим
   `app.py` обязан положить `session["ai_history"] = []` (пустой список,
   не `None`) — тогда один и тот же объект списка растёт от вызова к
   вызову и виден в сессии без дополнительной передачи наружу.
4. **История диалога сбрасывается при каждом новом входе в экран
   «ИИ-консультант»** — уже согласовано с пользователем ранее в этом же
   цикле работы (см. диалог), включено сюда для полноты контракта.
5. **Эскалация вызывает `prepare_lead_draft` через синтетический ход
   модели**, не через прямой backend-вызов `agent_tools.prepare_lead_draft`
   в обход модели. Причина: `service`/`agent_summary`/`missing_info`
   обязаны формироваться моделью по уже согласованному контракту
   (`spec.md`, раздел 5) — backend не может их придумать сам. Клик «Хочу
   оставить заявку» отправляет в `run_agent` служебное сообщение вида
   «Пользователь хочет оставить заявку — подготовь черновик» (роль
   `user`, но текст фиксированный, не введённый пользователем), модель
   решает вызвать `prepare_lead_draft` на основе уже накопленной
   `session["ai_history"]`.
6. **Плейсхолдер поля ввода остаётся статичным** («Введите сообщение»,
   `static/index.html`) — специфичный текст «Задайте Ваш вопрос» для
   экрана ИИ-консультанта (`docs/bot-ux-flow.md`, раздел 6) технически не
   реализован в этой фазе: потребовал бы либо динамической правки DOM по
   `mode` в `script.js` (не сложно), либо нового поля в `ChatResponse`.
   Признано мелкой, не блокирующей критерии приёмки деталью — отложено,
   не точка роста (тривиально доделать позже при желании), просто не в
   этом цикле.
7. **Валидация контакта переиспользуется из `bot_flow.py` — чисто
   аддитивно, без изменения существующей логики** (пересмотрено после
   вопроса пользователя, см. Шаг 2). `grep` подтвердил: `handle_lead_input`/`submit_feedback`
   делают **инлайн**-проверки (`len(...) < 2`, `_EMAIL_RE.match(...)`), не
   вызывают общую функцию — переписывать их под новую функцию означало бы
   менять уже протестированный рабочий код `bot_flow.py` без необходимости.
   Вместо этого: добавляется новый публичный алиас `EMAIL_RE = _EMAIL_RE`
   (старое `_EMAIL_RE` и весь код, который его использует, — не трогается)
   и новая отдельная `validate_contact_name(value) -> str | None` — обе
   только для нового кода `app.py` (контакт ИИ-консультанта). Ни одна
   строка внутри `handle_lead_input`/`submit_feedback` не меняется.
8. **Модель не участвует в сборе контакта, редактировании текста запроса
   и финальном сохранении.** Работа модели в сценарии эскалации
   заканчивается ровно на вызове `prepare_lead_draft` (Шаг 5) — дальше
   (Шаги 6, 8, 9: предпросмотр/редактирование текста, имя, email,
   финальный черновик, `save_confirmed_lead`) полностью backend/bot-flow-
   стиль, без единого обращения к модели. Модель вызывается снова только
   если пользователь после «Изменить» (Шаг 9) продолжает свободный чат и
   задаёт новый вопрос — это обычный чат, не часть сбора данных для
   заявки.
9. **Кнопка «Изменить» на финальном экране черновика** (после сбора
   контакта) переводит `session["mode"]` обратно в `"ai_consultant"` **без
   сброса `session["ai_history"]`** — это отличается от пункта 4 (сброс
   истории только при входе с главного экрана, не при внутреннем переходе
   «Изменить» → чат в рамках уже начатой эскалации). Совпадает с уже
   зафиксированным в `docs/bot-ux-flow.md`, раздел 11: «Изменить» — «возврат
   в свободный чат для уточнения текстом».
10. **`prepare_lead_draft` при повторном вызове (после «Изменить» → новый
    диалог → новая эскалация) перезаписывает `session["lead_draft"]`
    целиком** — это уже поведение самой функции (`Plan-tools.md`, Шаг 4),
    этот план его не меняет, только явно фиксирует, что это ожидаемо при
    повторном проходе через «Изменить».

## 1.1 Целевой сценарий

Пользователь открывает чат → нажимает «Перейти к ИИ-консультанту» →
видит пустой экран с активным полем ввода (плейсхолдер «Введите
сообщение») → печатает вопрос, на который в `knowledge/` есть ответ →
получает ответ со ссылкой на материал и видит кнопку «Хочу оставить
заявку» под ответом (видна всегда, см. `spec.md` раздел 11). Печатает
второй вопрос, ответа на который в базе нет → бот честно говорит об этом
→ нажимает «Хочу оставить заявку» → видит предпросмотр «Вот как я понял
ваш вопрос: ...» с кнопками «Уточнить вопрос»/«Да, это мой запрос» →
нажимает «Уточнить вопрос» → видит то же поле, предзаполненное текстом,
редактирует и отправляет → бот запрашивает «Как к Вам обращаться?» → имя
→ «Укажите корпоративную почту» → email → видит финальный черновик
(услуга/текст/контакт/что известно/чего не хватает) с кнопками «Отправить
заявку»/«Изменить»/«Отмена» → нажимает «Отправить заявку» → видит
сообщение с номером заявки → проверяет в SQLite: строка с
`source="ai_consultant"`, `status` соответствует `missing_info`.

  раздел 11, уже зафиксировано);
