# spec.md — ЮрСправочник

## 1. Краткое описание

Веб-чат с ИИ-консультантом по внутренней базе знаний юридического отдела компании. Пользователь (сотрудник компании) получает консультацию по трём предметным юридическим направлениям — согласование договоров, 152-ФЗ о персональных данных, согласование сделок — и может оставить обычную заявку через сценарный bot-flow или обратиться к ИИ-консультанту, который отвечает по базе знаний и готовит черновик обращения для подтверждения. Bot-flow и ИИ-консультант — универсальный технический слой, одинаково обслуживающий любую из трёх услуг. Проект — учебный MVP, реализуемый за 24 часа, с запуском локально и на VPS как единый Python runtime.

## 2. Цели

- Один воспроизводимый web-чат бот с интерфейсом, обычным bot-flow и ИИ-консультантом.
- ИИ-консультант отвечает только по материалам компании (`knowledge/`), готовит черновик обращения и сохраняет его только после подтверждения пользователем.
- Обычная заявка, заявка из ИИ-консультанта и обратная связь сохраняются в SQLite и различимы по `source`.
- Проект запускается локально и поднимается на VPS как тот же runtime.

## 3. Не-цели

Явно исключено из MVP (зафиксировано как «опасные точки» — не начинать до прохождения базовых сценариев):

- Загрузка и анализ пользовательского файла.
- Автоматическая проверка договора по чек-листу.
- Генерация полного юридического документа.
- Векторная БД, embeddings, внешний RAG-сервис.
- Авторизация, роли, личный кабинет.
- Интеграции с СЭД, 1С, e-mail, Telegram.
- Реальная отправка обращения в корпоративную систему.
- Домен, публичная ссылка, отдельный production-контур.
- Cookie-based auth, Redis, распределённые сессии, персональная долгосрочная память.

## 4. Пользователи и сценарии

**Пользователь:** сотрудник компании, которому нужна консультация юридического отдела по типовому вопросу или помощь в подготовке обращения.

**Основной сценарий:**
1. Открывает web-чат, видит главное меню и поле ввода.
2. Открывает «Услуги» или «FAQ».
3. Создаёт обычную заявку через сценарный bot-flow (без обращения к модели).
4. Запускает ИИ-консультанта, задаёт вопрос по услугам/правилам.
5. Получает ответ на основе `knowledge/` через AI Studio API.
6. Просит помочь с обращением — видит черновик с действиями «Отправить», «Изменить», «Отмена».
7. Подтверждает черновик — заявка сохраняется в SQLite с `source = ai_consultant`.
8. Обычная заявка, AI-заявка и обратная связь различимы в данных.

## 5. Функциональные требования

**Услуги (3, каталог MVP, см. `knowledge/services.md`):**
1. Консультация по порядку согласования договоров — обязательные (существенные) условия договора, этапы согласования по внутреннему регламенту визирования.
2. Консультация по 152-ФЗ о персональных данных — ответы с цитированием статьи закона и пояснением простыми словами.
3. Консультация по согласованию сделок — критерии обязательности корпоративного согласования (сумма, характер сделки/отчуждение, крупная сделка, сделка с заинтересованностью), что готовить инициатору и с кем согласовывать.

Bot-flow и ИИ-консультант — универсальный технический слой доставки, одинаково обслуживающий любую из трёх услуг (услуги различаются по юридической тематике, а не по механике бота).

**FAQ (минимум 4 категории):** услуги, SLA/сроки/приоритет обращения, формат работы, правила/контакты.
*(Категория «стоимость» из типовой формулировки урока переосмыслена как SLA/сроки/приоритет — сервис внутренний, для сотрудников компании, без внешнего ценообразования.)*

**Обычный bot-flow** (без LLM, работает даже без ключа/лимита AI Studio):
- Главное меню: Услуги, FAQ, Оставить заявку, ИИ-консультант, Обратная связь — пять самостоятельных пунктов верхнего уровня.
- «Оставить заявку» начинается с явного шага выбора услуги (те же три пункта каталога — согласование договоров / 152-ФЗ / согласование сделок), и только затем запрашивает контакт и краткое описание задачи; выбранная услуга заполняет поле `service` в `leads`.
- Неизвестный ввод не ломает сценарий.
- Обычная заявка и обратная связь сохраняются в SQLite независимо друг от друга.

**ИИ-консультант:**
- Отвечает только по материалам `knowledge/services.md`, `knowledge/faq.md`, `knowledge/rules.md`.
- Задаёт 1–2 уточняющих вопроса, помогает выбрать услугу.
- Не выдумывает данные, которых нет в `knowledge/`; при отсутствии информации — честно сообщает и предлагает оставить заявку.
- Готовит черновик заявки: услуга, краткое описание задачи, контакт, что известно, чего не хватает, исходный запрос/выжимка.
- Черновик сохраняется в `leads` только после явного подтверждения (`save_confirmed_lead`), не автоматически.

**Tools агента** (безопасные, whitelisted):
- `search_knowledge` — поиск только внутри `knowledge/`.
- `read_knowledge_file` — не читает `.env`, абсолютные пути, файлы вне `knowledge/`.
- `prepare_lead_draft` — создаёт только черновик.
- `save_confirmed_lead` — сохраняет только после подтверждения.

**Данные заявки (поле `contact` в `leads`):** внутренний контакт сотрудника — ФИО + внутренний канал связи, указанный как обычная текстовая строка (например, имя пользователя в Telegram или email для связи) — без интеграции с Telegram API или иным мессенджером; бот не отправляет и не читает сообщения через эти каналы, только сохраняет контакт как текст. Запрещено запрашивать: персональные документы, номера карт, иные избыточные персональные данные.

**Хранение данных (SQLite `data/bot.sqlite3`):**
- `leads(session_id, source, service, contact, problem_text, agent_summary, missing_info, status, created_at)`.
- `feedback(session_id, message_text, created_at)`.
- `source` различает `bot_flow` и `ai_consultant`.
- `status` определяется автоматически при создании записи на основе уже собранных данных, без ручного вмешательства: `"new"`, если `missing_info` пусто (данных достаточно, включая все `bot_flow`-заявки), либо `"needs_clarification"`, если ИИ-консультант эскалировал вопрос с непустым `missing_info`. Автоматических переходов между статусами после создания в MVP нет — дальнейшая обработка юристом происходит вне системы (см. `knowledge/rules.md`, «Регламент обращения»).
- `agent_summary` и `missing_info` осмысленны только для `source = ai_consultant`; для `source = bot_flow` эти поля остаются `NULL`/пустыми.
- Сам файл `data/bot.sqlite3` не коммитится (`.gitignore`: `data/*.sqlite3*`, включая WAL/SHM-спутники) — в git попадает только код схемы. Приложение обязано создавать файл и таблицы автоматически при старте (`CREATE TABLE IF NOT EXISTS ...`), чтобы после `git clone` на VPS/другой машине БД появлялась без отдельного ручного шага инициализации (`urok.md`, критерий Фазы 6: «SQLite создаётся или подключается по ожидаемому пути»; Фаза 7 требует отдельную инструкцию в README только если инициализация не автоматическая).

**Управление сессией чата:**
- `session_id` генерируется backend при первом обращении к `/api/chat` и возвращается в JSON-ответе.
- Активный контекст диалога (история сообщений, состояние bot-flow, состояние agent loop, несохранённый черновик заявки) хранится в памяти единственного FastAPI runtime по ключу `session_id` — не в SQLite.
- Frontend по умолчанию хранит `session_id` в рамках текущей страницы. Допустимо дополнительно кэшировать его в `localStorage` как необязательный UX-слой для устойчивости к случайному reload во время ручного тестирования — при отсутствии соответствующей серверной сессии backend создаёт новую и возвращает новый `session_id`, frontend обновляет закэшированное значение.
- `localStorage`/persistence не используются для истории сообщений, черновиков, персональных данных или секретов.
- После перезапуска runtime активные (неподтверждённые) сессии и черновики могут быть потеряны — это допустимо; подтверждённые заявки и feedback уже в SQLite и не зависят от process-memory.

## 6. Нефункциональные требования

- Один Python runtime (FastAPI + uvicorn), Python 3.13.x, venv.
- Логи не раскрывают секреты, API-ключи и лишние персональные данные.
- Защита tools от выхода за пределы `knowledge/` и от чтения `.env`.
- `.env` не коммитится; `.env.example` содержит только имена переменных с плейсхолдерами.
- Локальный запуск и запуск на VPS воспроизводимы по README.
- **Сбой AI Studio API в середине сессии** (сеть, таймаут, 429/квота, 401/ключ) не роняет процесс: вызов модели в `agent_runtime.py` оборачивается в `try/except`, пользователю возвращается дружелюбное сообщение об временной недоступности с предложением воспользоваться обычным меню; история диалога и `session_id` не сбрасываются; в лог пишется только класс ошибки, без секретов и стектрейса. Bot-flow при этом продолжает работать независимо (см. раздел 5).
- **Защита от двойного подтверждения заявки:** frontend блокирует кнопку «Отправить заявку» сразу по клику до ответа backend. Backend дополнительно — как idempotency-guard — очищает `session["lead_draft"] = None` сразу после успешного `save_confirmed_lead`; повторный запрос на подтверждение при уже пустом черновике не создаёт вторую запись в `leads`, а возвращает ответ «заявка уже отправлена». Реальное прерывание уже начатого запроса к модели (отмена генерации на середине) — не часть MVP, зафиксировано как точка роста (раздел 11).

## 7. Технический подход

| Компонент | Решение | Обоснование |
|---|---|---|
| Backend | FastAPI + uvicorn | Единый ASGI-процесс = один Python runtime; встроенная pydantic-валидация переиспользуется и для HTTP-слоя, и для аргументов tools; неблокирующий I/O на время ожидания ответа AI Studio API. |
| AI-клиент | `openai` SDK, `client.chat.completions.create(...)` | Подтверждено и паттерном терминального урока (`agent-py.md`), и официальной документацией AI Studio для function calling — только этот метод возвращает `message.tool_calls` в нужном формате для agent loop. `client.responses.create(...)` используется в документации только для одиночных запросов без tool calling — не подходит. |
| Модель | `gpt-oss-120b/latest` через `YANDEX_MODEL_URI` | Модель из терминального урока, размера достаточно для задач поиска по базе знаний и коротких ответов. |
| Хранилище бизнес-данных | SQLite (`sqlite3`, стандартная библиотека) | Файл `data/bot.sqlite3`, без дополнительных зависимостей. |
| Frontend | Статические HTML/CSS/JS, без фреймворка | Прямое требование границ проекта — «обычные HTML/CSS/JS-файлы для интерфейса». |
| Сессия чата | Backend-generated `session_id` + in-memory context | См. раздел 5 «Управление сессией чата». |

*(Явный план реализации по слоям `interface` / `backend` / `database` / `agent`, требуемый Фазой 1 `urok.md`, зафиксирован в `README.md`, раздел «План реализации по слоям» — не дублируется здесь во избежание рассинхронизации двух копий одного и того же списка.)*

## 8. UX-потоки

**Web-интерфейс:** одна страница чата с историей сообщений в рамках сессии, главным меню (Услуги / FAQ / Оставить заявку / ИИ-консультант / Обратная связь) и полем текстового ввода.

**Bot-flow:** пользователь выбирает пункт меню → получает соответствующий контент/форму → заполняет обычную заявку или feedback → подтверждение сохранения.

**ИИ-консультант:** пользователь задаёт вопрос → агент ищет по `knowledge/` через `search_knowledge`/`read_knowledge_file` → отвечает или честно сообщает об отсутствии информации → при готовности предлагает черновик заявки (`prepare_lead_draft`) → пользователь видит черновик и три действия: «Отправить заявку» (`save_confirmed_lead`), «Изменить» (возврат к уточнению), «Отмена» (черновик не сохраняется).

## 9. Этапы реализации (по `project_plan_24h.md`)

0:00–1:30 Спецификация (`spec.md`, `Plan.md`, `AGENTS.md`) → 1:30–3:00 Knowledge base → 3:00–4:30 Основа runtime (`.env.example`, `ai_client.py`, `agent/soul.md`, `agent_runtime.py`, проверка биллинга AI Studio) → 4:30–6:00 Безопасные tools → 6:00–7:30 SQLite → 7:30–10:00 Обычный bot-flow → 10:00–13:00 Web UI → 13:00–15:30 AI-сценарии → 15:30–17:00 Confirmation flow → 17:00–19:00 Тестирование → 19:00–20:30 README → 20:30–22:00 VPS → 22:00–24:00 Доказательства (5 скриншотов).

Порог готовности к 17-му часу: web-чат работает локально, bot-flow работает без `.env`, FAQ/каталог доступны, обычная заявка и feedback сохраняются раздельно, AI-консультант отвечает только по `knowledge/`, черновик не сохраняется без подтверждения.

## 10. Критерии успеха

Соответствуют критериям приёмки фаз 1–7 в `urok.md`: работающий локальный сценарий (bot-flow + ИИ-консультант + подтверждение + SQLite), отказ ИИ-консультанта на попытку прочитать `.env`/файл вне `knowledge/`, воспроизводимый запуск на VPS, README с полной инструкцией, 5 обязательных скриншотов без секретов и лишних персональных данных, заметка о проверке биллинга/лимитов AI Studio.

## 11. Риски и компромиссы

- **Сжатый таймлайн (24ч):** снижается за счёт переноса проверенного паттерна терминального урока «почти без изменений» вместо разработки с нуля.
- **FAQ-категория «стоимость» неприменима к внутреннему сервису** — решено переосмыслением в SLA/сроки/приоритет, без нарушения формального требования об 4 категориях.
- **`session_id` без обязательной persistence** — при перезапуске runtime активный диалог теряется; принято как допустимое для MVP, так как подтверждённые данные (`leads`, `feedback`) в SQLite не зависят от memory.
- **Неполная документация провайдера (AI Studio)** — обнаружена опечатка в официальном примере function calling (`function_args.get("get_current_weather")` вместо `"location"`); учтено в `ai_studio_api_notes.md`, не будет повторено в собственном коде.
- **Объём базы знаний (`knowledge/services.md`, `faq.md`, `rules.md`) намного превышает ориентир 1 500–2 500 слов из `project_plan_24h.md`** — сейчас включает полный текст регламента визирования договоров с приложениями и дословные статьи 152-ФЗ с разъяснениями. Риск в трёх конкретных местах, а не в «природе текста»:
  1. Каждый запрос к AI Studio передаёт содержимое найденного файла в промпт — больше текста = больше токенов и стоимости на **каждый** вызов, не разово (`YANDEX_MAX_TOKENS=10000` ограничивает только ответ, не входной контекст).
  2. Ручная проверка в Фазе 5 («ИИ-консультант не выдумывает... если их нет в `knowledge/`», `urok.md:105`) требует сверки каждого конкретного факта/цифры в ответе модели — чем больше фактов в файле, тем больше ручной работы за отведённые 17:00–19:00.
  3. При поиске по большому файлу с разнородным юридическим текстом выше шанс, что `search_knowledge` подтянет смежный, но не совсем релевантный фрагмент.

  Решение по сокращению не принято — зафиксировано как риск, к которому нужно вернуться перед тестированием ИИ-консультанта (Фаза 5, `project_plan_24h.md`, 17:00–19:00).
- **Точка роста — дальнейшие переходы `status` после создания записи.** В MVP `status` принимает одно из двух значений только в момент создания (`"new"` / `"needs_clarification"`, на основе `missing_info`) и не меняется автоматически. Переходы вида «в работе» / «закрыта» требуют кабинета юриста или другого интерфейса для ручной пометки — такого интерфейса в MVP нет и не будет («отдельный кабинет управления» исключён урок.md), поэтому дальнейшая эволюция `status` — расширение вне текущего MVP, не техдолг.
- **Точка роста — прерывание генерации ответа модели.** В MVP кнопка «Отправить заявку» блокируется на время ожидания ответа (см. раздел 6), но отмена уже начатого запроса к AI Studio на середине генерации не реализуется — это отдельная задача (asyncio task cancellation, сигнал от frontend, гонка с уже пришедшим ответом), не входящая ни в один критерий приёмки `urok.md`. Не требуется для MVP.
- **Порядок выполнения отличается от «Стратегии реализации» в `project_plan_24h.md`.** Раздел «Стратегия реализации» того документа советует обратный порядок («сначала обычный чат + SQLite без AI, затем AI Studio + tools, затем web-интерфейс»). Фактически работа идёт по почасовой таблице того же файла, где перенос паттерна терминального урока (knowledge base → runtime → tools) стоит **раньше** интерфейса/bot-flow/SQLite — осознанный выбор в пользу более детального почасового плана, а не следование общему принципу «Стратегии». `urok.md` не требует конкретного порядка выполнения его 7 фаз — только чтобы к 24-му часу все критерии приёмки были закрыты; порядок тайм-слотов внутри `project_plan_24h.md` объединяет и переставляет фазы `urok.md` (например, Фаза 3 `urok.md` выполняется раньше Фазы 2). Несоответствие двух разделов одного файла — особенность источника, не ошибка текущей реализации.
